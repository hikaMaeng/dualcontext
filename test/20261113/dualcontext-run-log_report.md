# 시험 실행 로그(목록 · 상세) 검증 기록

대상: 배포된 컨테이너(`127.0.0.1:18081`). 요구: 「시험 실행의 로그를 남겨서 리스트와 상세보기를 해줘」.

## 계획(수락 기준)

| # | 기준 |
| --- | --- |
| 1 | 시험 실행마다 로그가 남는다. 성공뿐 아니라 실패도 남는다. |
| 2 | 로그 목록 화면이 있다. |
| 3 | 로그 상세 화면이 있다. 결과를 이해하는 데 필요한 정보(질의, 설정, 선택된 쌍, 자료, 컨텍스트, 실패 사유)가 들어 있다. |

## 실행 결과

| # | 실행 | 관측 | 판정 |
| --- | --- | --- | --- |
| 1 | API: 정상 질의 2건 | 로그 `#1`(964ms), `#2`(2000ms), 둘 다 `status=ok`, 라우팅 `embedding` | 통과 |
| 2 | 임베딩 서버 주소를 죽은 포트로 바꾸고 실행 | `#3 ok 21ms`, 라우팅 `embedding-failed(fetch failed)->keyword-fallback-all`, 두 쌍 모두 `mat=0 err=fetch failed`. 설정은 원복 | 통과(되돌림이 로그에 남음) |
| 3 | 조사원 테이블을 잠깐 `researchers_x` 로 개명하고 실행 | HTTP 502 `{"error":"relation \"researchers\" does not exist","runId":4}`, 목록에 `#4 error 3ms`. 테이블 원복 후 조사원 6개 확인 | 통과(실패 로그) |
| 4 | 브라우저: 시험 실행 → 질의 입력 → 실행 | `logged-state` = 「실행 로그에 저장했습니다: #5」, 링크 `#runs` | 통과 |
| 5 | 브라우저: 링크로 이동 → 목록 | 항목 5개(#5~#1), 각 항목에 번호 · 시각 · 성공/실패 · 질의, 실패 항목(#4)은 「실패」 | 통과 |
| 6 | 브라우저: #5 선택 → 상세 | 제목 「실행 상세 #5」, 라우팅 `embedding`, 소요 3.0초, 설정 스냅샷 키 `chat, router, writer, embedding`, 쌍 2개(자료 3 · 5건), 컨텍스트 본문. 상세 텍스트에 `apiKey`/`api_key` 문자열 없음 | 통과 |
| 7 | 레이아웃 | 첫 배포에서 긴 질의가 목록 열 밖으로 넘쳐 상세와 겹쳤다 → 그리드 트랙을 `minmax(0,1fr)` 로 고정하고 말줄임 적용 후 재배포, 스크린샷으로 해소 확인 | 통과(수정 후) |
| 8 | i18n · 아키텍처 · compose · docs 검사, 타입 검사, 단위 테스트 | 위반 0, 오류 0 (단위 테스트 16건: app 7 + domain 9) | 통과 |

## 발견

* 잘못된 임베딩 **모델 이름**(`no-such-model`)으로는 실패가 나지 않고 정상 임베딩 라우팅이 됐다(로그 `#2`). 이 서버가 알 수 없는 모델 이름을 무시하는 것으로 보이며, 이 경우 설정 오타가 조용히 통과한다. 확인한 것은 이 동작뿐이고 원인(서버 구현)은 확인하지 못했다.
* 임베딩 서버가 죽으면 키워드 폴백이 「맞는 키워드 없음 → 사용 가능한 조사원의 앞 N 개」로 가서 질의와 무관한 조사원(법률 용어 · 판례)이 선택됐다(로그 `#3`, GDP 질의). 폴백이 로그에 남아 알 수는 있지만 선택 자체는 임의다.

## 검증하지 못한 것

* 로그 500건 상한의 자동 삭제는 동작을 확인하지 않았다(코드로만 존재).
* 로그 삭제 버튼과 ko 외 언어 화면은 누르지 않았다.
* LLM 라이터(수 분 소요) 실행의 로그는 이번에 남겨 보지 않았다.
* 설정 스냅샷을 읽는 단계의 실패(DB 장애)는 로그를 남기지 못한다(설계상).
