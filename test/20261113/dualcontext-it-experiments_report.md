# IT 분야 확장과 복합 질의 실험 종합

요구: 「컴퓨터 · 인공지능 · GPU 등 더 다양한 IT 분야 데이터셋으로 조사원과 프로시저를 Codex 서브 세션 여럿에게 추가시키고, 복합 질의(조사원 둘 이상, 한 조사원에 프로시저 둘 이상, 판단이 필요한 정보)를 던지는 실험 세션도 운영한다.」

세션은 모두 `codex exec -m gpt-6.1-terra -c model_reasoning_effort=medium`(workspace-write, 작업 폴더 밖 쓰기 차단)이다. 지시문 · 런처 · 각 세션의 최종 보고는 `codex-sessions/` 에 있다.
세션의 보고를 그대로 믿지 않고, 매번 `domain.json`/`queries.json` 의 작성 시각, 허깅페이스 API 의 라이선스, `--dry-run` 재실행, `runs/*.json` 원자료와 대조했다.

## 1. 데이터 분야 추가(D1~D5)

| 세션 | 분야 | 데이터셋 | 라이선스(카드 기준) | 적재 행 | 내가 다시 확인한 것 |
| --- | --- | --- | --- | --- | --- |
| D1 | GPU 하드웨어 | Intelion/gpuark-gpu-dataset (`gpu_specs`) | cc-by-4.0 | 300 | dry-run 300행, 빈 행 0 |
| D2 | AI·ML 논문 | kiyer/arxiv_cs.LG | mit | 300 | dry-run 300행, 빈 행 0 |
| D3 | 소프트웨어 개발 | code-rag-bench/stackoverflow-posts | cc-by-sa-4.0 | 300 | dry-run 300행, 빈 행 0 |
| D4 | 보안(CVE) | AlicanKiraz0/All-CVE-Records-Training-Dataset | apache-2.0 (합성 가공) | 300 | dry-run 300행, 빈 행 0 |
| D5 | 미국 기업 뉴스 | KrossKinetic/SP500-Financial-News-Articles-Time-Series | mit | 300 | dry-run 300행, 빈 행 0 |

* 5개 모두 `gated=false`. 조사원 5개 + 프로시저 19개가 등록됐다(조사원 총 11, 프로시저 총 27).
* 세션 보고와 달랐던 점: **D4 는 「행 API 429 로 dry-run 실패」라고 보고**했지만 재시도를 넣은 내 스크립트로는 통과했다. **D1 은 「적재기의 행 수 계산 문제」로 100행으로 줄였고** 앞 100행의 98%가 2015년 이전 제품이었다. 원인은 내 스크립트가 구성(config)별 행 수가 아니라 데이터셋 전체 행 수로 표본 오프셋을 잡은 것이라 고쳤다(`gpu_specs` 13,566행 vs 전체 14,559행).
* D1 표본 300행의 출시 연도: 2015 미만 184 · 2015~19년 106 · 2020년 이후 8 — 이 데이터셋 자체가 오래된 제품 위주다.
* D5 는 CNBC 기사 본문이라 허깅페이스의 MIT 표기가 기사 자체의 재배포 권한을 보증하지 않는다. 로컬 시험용으로만 쓴다.
* D3 · D4: 큰 코퍼스(StackOverflow 약 197만 행, CVE 약 29.7만 행)의 300행 표본이라 일반 질문의 적중률은 낮다.

## 2. 복합 질의 실험(E1b~E3b: 기존 5개 분야, F1~F3: IT 분야)

공통: 질의 4개씩 · 정답 사실을 **실행 전에** `queries.json` 에 고정(원문 인용 포함, 작성 시각이 첫 실행보다 앞섬을 확인) · 사실 단위 hit/partial/miss/contradict 채점 · 사후 변경 금지(무효는 `invalid` 로 표시). 채점자는 모델이다.

| 세션 | 주제 | 증강 전 → 후 적중(세션 보고, 정확 hit 만) | 비고 |
| --- | --- | --- | --- |
| E1b | 조사원 교차(기존 5분야) | 양쪽 답변이 있는 질의 0/5 → 4/5 | 증강 전 2건 타임아웃. 사실 3개 무효 처리 |
| E2b | 한 조사원 · 복수 프로시저 | 원시 0/3 → 4/9 (분모 다름, 비교 불가) | 양쪽 답변이 모두 생성된 유효 질의 없음 |
| E3b | 모순 · 부분 · 최신 · 범위 밖 | 0/5 → 2/5 | 기대 조사원 · 프로시저 정확 일치 0건 |
| F1 | IT 조사원 교차 | 전체 2/12 → 12/16, 같은 질의(Q1~Q3)만 2/12 → 8/12 | Q4 증강 전 `fetch failed` |
| F2 | IT 한 조사원 · 복수 프로시저 | 0/4 → 2/13 (비교 불가) | 8개 답변 중 4개 `fetch failed` |
| F3 | IT 최신성 · 모순 · 교차 언어 · 범위 밖 | 3/14 → 9/14 | 답변 8개 모두 생성 |

**이 표의 숫자는 세션끼리 직접 비교할 수 없다**(질의 · 분모 · 채점 기준이 다르다). 의미 있는 것은 방향과 사례다.

### 확인된 사실(원자료로 직접 센 값)

* **최종 답변 48개 중 12개가 만들어지지 않았다.** E 라운드 24개 중 7개(`AbortSignal` 300초), F 라운드 24개 중 5개(`fetch failed`). 12건 모두 경과 시간이 300~301초다. 따라서 E1b · E2b · F1 · F2 의 「전후 비교」는 표본이 크게 줄었고, 이 실험의 증강 효과 수치는 **결함 있는 측정 조건**에서 나온 것이다.
* 라우팅: 기대 조사원이 빠짐없이 선택된 질의는 많았지만 **기대 프로시저가 모두 선택된 질의는 소수**였고, 질의마다 무관한 조사원이 1~2개씩 끼었다(상위 3 고정). 웹 검색 조사원은 E1b · E2b 8개 질의 모두에 선택됐다.
* 증강이 도움이 된 대표 사례: 질의에서 고유 사실을 요구할 때 증강 전 답변이 그럴듯하게 틀렸다(예: F3-1 구형 GPU 두 제품의 사실 4개를 모두 틀리게 제시, F1-Q1 MSI GT 330 의 대역폭 14.4 GB/s · 권장 300 W 를 제시했으나 자료는 25.60 GB/s · 250 W). 증강 후는 자료에 맞게 바뀌었다.
* 증강이 해가 된 사례: F1-Q3 에서 증강 전 답변은 `mysql_real_escape_string` 을 맞혔는데, 해당 행의 본문이 600자에서 잘려 증강 후에는 확인하지 못했다(hit → miss). F3-4 에서 범위 밖 질의에 증강 후 답변이 무관한 자료를 인용하지는 않았지만 답변 전체를 보류해 증강 전(설명 제공)보다 유용성이 떨어졌다.

## 3. 실험이 드러낸 결함 두 가지와 수정

### (1) 컨텍스트 자료 600자 절단

검색은 정답 행을 찾았는데 컨텍스트에 600자만 실려 정답 문장이 사라지는 사례가 F1 에서 3건(Q1 · Q2 · Q3), F2 · F3 에서도 확인됐다. `snippetChars`(조사원 설정, 기본 1200)를 도입했다.

고정된 질의 12개(F1 · F2 · F3, 조사원 11개 시점으로 동일)의 정답 인용문이 컨텍스트에 들어 있는지를 수정 전(저장된 실행)과 수정 후(MCP 새 호출)로 **같은 기준**으로 셌다(`evidence-recheck.mjs`, 결과 `evidence-recheck_result.json`):

| 기준 | 수정 전 | 수정 후 |
| --- | --- | --- |
| 정답 인용 포함 사실(47개) | 25 | **31** |
| 인용 40자 이상만(24개, 짧은 인용의 우연 일치 배제) | 8 | **14** |
| 세션별 | F1 12/16 · F2 4/17 · F3 9/14 | F1 15/16 · F2 6/17 · F3 10/14 |

* 변화가 있던 6개 사실은 모두 `false → true` 이고 퇴보는 0건이다.
* 이것은 **컨텍스트에 정답 근거가 실렸는가**의 결정적 측정이며 최종 답변의 품질 측정이 아니다. 수정 후 답변은 다시 만들어 채점하지 않았다.
* 남은 미포함 16개는 대부분 **검색 자체 실패**다(F2-2: CVE 번호 3건 중 0건 검색). 식별자 정확 일치가 약한 임베딩 검색의 한계로, 키워드 검색과 섞는 하이브리드가 다음 후보다.

### (2) 채팅 호출이 정확히 300초에 끊김

가설: Node 내장 `fetch`(undici)의 `headersTimeout` 기본 300초. 추론 모델은 비스트리밍 응답에서 답이 끝나야 헤더를 보내므로 `AbortSignal` 을 늘려도 300초에 끊긴다.

| 검증 | 결과 |
| --- | --- |
| 응답 헤더를 320초 뒤에 보내는 가짜 서버(`slow-header-probe.mjs`), 수정 전 코드 | **306.7초 `fetch failed`, 원인 `UND_ERR_HEADERS_TIMEOUT`** |
| 같은 프로브, 수정 후 코드(`undici` `Agent` headersTimeout · bodyTimeout 900초) | **320.0초 정상 응답** |

* 실제 LLM 서버로 300초를 넘기는 시험 실행은 수정 후에 돌리지 않았다. 프로브가 증명하는 것은 「클라이언트가 300초를 넘는 지연을 견딘다」까지다.
* 이 수정 이전에 내가 `AbortSignal` 만 900초로 올렸을 때 해결됐다고 판단했던 것은 틀렸다(F 라운드 5건이 그 뒤에 `fetch failed` 로 실패).

## 4. 반증되었거나 정정한 것

* 「타임아웃은 `AbortSignal` 300초가 원인」 → E 라운드 7건은 맞았지만 F 라운드 5건은 undici 300초였다.
* 내가 중간 보고에서 말한 「답변 8개 중 5개 · 6개 실패」는 틀린 수치였다. 정확한 값은 위 「확인된 사실」(48개 중 12개; E 24개 중 7, F 24개 중 5).
* 세션 D4 의 「dry-run 실패」, D1 의 「적재기 행 수 계산 문제」는 각각 재시도 부재와 내 스크립트의 구성별 행 수 결함이었다.
* 실험 세션 첫 시도(E1~E3)는 샌드박스 오류로 20초 만에 실패했다: Windows 샌드박스는 서로 다른 쓰기 허용 경로 집합을 동시에 적용하지 못한다. 모든 세션이 같은 작업 폴더를 쓰도록 바꿔 해결했다.

## 5. 이 종합이 보증하지 못하는 것

* 증강 후 답변이 항상 낫다는 근거가 아니다. 표본은 질의 24개 · 정답 사실 약 100개이고 모델이 채점했다. 외부 사실 검증과 반복 실행은 하지 않았다.
* `snippetChars` 수정 후의 **최종 답변 품질**은 재측정하지 않았다(컨텍스트 포함 여부만 측정).
* 합성 데이터(산업 뉴스 · 금융 시황 · CVE)는 실제 사실이 아니다.
* 라우터 설정이 실험 중 조사원 상위 3 · 프로시저 상위 2 로 바뀐 상태다(실행 로그의 설정 스냅샷에 남음). 1라운드(E)와 2라운드(F)는 등록된 조사원 수가 달라(6개 → 11개) 라우팅 비교는 불가능하다.
* 시험 질의가 실행 로그에 쌓인다(상한 500건).
