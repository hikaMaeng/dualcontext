# 「마땅한 조사원 없음」 판정과 비동기 실행 검증 기록

요구 1: 「27번(빵 반죽 질문)처럼 마땅한 조사원이 없는 질의에 엉뚱한 조사원이 붙었다. 마땅한 연구원이 없다는 판정도 할 수 있어야 하고, 그럴 때 추가 컨텍스트를 공급하지 않아야 한다.」
요구 2: 「비동기적인 실행과 SSE 또는 폴링으로 대응하라.」
질문: 「결국 라우터를 LLM 으로 운영해야 하나?」

## 1. 재현과 수정

* 실행 로그 `#27`: 라우터가 상위 3개를 억지로 채워 소프트웨어 개발 · 의학 · 기업 뉴스 조사원을 붙였다(원인: 임베딩 라우팅에 최소 유사도 기준이 없고, 키워드 폴백도 「맞는 게 없으면 전부」였다).
* 수정: 임베딩 라우팅에 최소 유사도(기본 0.67), 키워드 폴백을 「없음」으로, 선택 0개면 컨텍스트를 비우고 라이터를 부르지 않음, MCP 는 빈 결과, 시험 실행은 증강 후 답변을 만들지 않음, 후보별 라우팅 점수를 실행 로그에 저장.
* 같은 질의로 재현(`?wait=1`): 라우팅 `embedding`, 선택된 쌍 0개, 컨텍스트 `""`, 라이터 호출 0회, 점수표 최고 0.6532(소프트웨어 개발)가 모두 `[제외]`, 증강 후 답변 `{skipped:true}`.

## 2. 기준값 0.67 의 근거(측정)

`routing-calibration.mjs`: 실험 질의 + 무관 질의 24개로 질의와 조사원 설명 사이 코사인 유사도를 쟀다. 기대 조사원이 있는 질의 23개 vs 무관·범위 밖 질의 25개(무관 24 + 설계상 범위 밖 F3-4).

| 판정 규칙(질의에 마땅한 조사원이 있는가) | AUC |
| --- | --- |
| 1위 점수의 절대값 | **0.988** |
| 1위 − 전체 평균 | 0.899 |
| 1위 − 2위 | 0.853 |
| 조사원별 표준화 z 의 최대 | 0.984 |

| 기준값 | 무관 질의가 「없음」(정답) | 정상 질의가 「없음」(오류) | 기대 (질의, 조사원) 쌍 유지 |
| --- | --- | --- | --- |
| 0.65 | 15/25 | 0/23 | 34/36 (94%) |
| 0.66 | 19/25 | 1/23 | 32/36 (89%) |
| **0.67** | **22/25** | **1/23** | **31/36 (86%)** |
| 0.68 | 23/25 | 1/23 | 27/36 (75%) |
| 0.70 | 25/25 | 5/23 | 19/36 (53%) |

* 27번 질의의 최고 점수가 0.6532 라 0.65 에서는 걸러지지 않는다. 0.655 이상이 필요했다.
* 출처: `routing-calibration_result.json` 의 `summary`(스크립트가 직접 계산한다). **검수에서 바로잡음**: 이 보고서의 앞선 표(AUC 0.990 · 0.67 에서 23/25 · 유지율 83%)는 근거 결과 파일이 비어 있는 채 커밋된 상태에서 적혀 있었다. 스크립트를 다시 돌려 위 값으로 고쳤고, 결론(0.67 근처, 1위 절대 점수가 가장 낫다)은 같다. 차이가 난 이유는 이전 실행의 점수를 복원할 수 없어 확정하지 못했다(설명 문구 조정 전후 임베딩 차이가 의심되나 검증하지 않았다).
* 한계: 점수가 0.5~0.85 에 압축돼 있어 경계(0.67~0.69) 질의는 어떤 기준값으로도 틀린다. 기준값은 이 데이터로 정해졌다(과적합 가능) → 아래 3 에서 새 질의로 검증.
* 오분류 한 가지를 바로잡았다: 처음에는 F3-4(제빵)와 E3b-4 를 양성에 섞었다. F3-4 는 설계상 범위 밖이라 음성으로 옮겼다(점수 하위 1위가 이 질의였다).

## 3. 새 질의 24개로 검증(기준값을 정할 때 쓰지 않은 질의, 라벨은 실행 전 고정)

`routing-heldout.mjs`(MCP, LLM 답변 없음) · `routing-llm-eval.mjs`(1단계만 LLM 라우팅). 양성 12(마땅한 조사원 있음) + 음성 12(컨텍스트가 비어야 함).

| 조건 | 임베딩 + 최소 유사도 0.67 | LLM 라우팅(qwen36-35b) |
| --- | --- | --- |
| 웹 검색 설명 = 「내부 자료에 없는 일반 사실을 웹에서」 | 양성 12/12 · 음성 11/12 | 양성 12/12 · **음성 1/12** |
| 웹 검색 설명 = 시점 민감 정보 전용으로 좁힘 | 양성 12/12 · 음성 10/12 | 양성 12/12 · **음성 12/12** |
| 호출 지연 | 임베딩 1회(약 1~2초) | 호출 하나 2.7~144.4초(중앙값 9.4) → 설명 조정 후 2.5~207.8초(중앙값 16.7) |

* LLM 이 첫 조건에서 틀린 11건은 전부 같은 원인이다: 웹 검색 조사원을 골랐다. 설명이 「일반 사실」을 맡는다고 해서 생긴 **논리적으로 맞는 판단**이다. 따라서 판정을 가른 것은 방식이 아니라 **웹 검색 조사원을 만능 폴백으로 둘지의 정책**이다.
* 설명을 좁힌 뒤 임베딩은 X2(사춘기 상담 → 소프트웨어 개발 조사원, 점수 0.6856)와 X11(현지 시장 흥정 → 웹 검색)에서 틀렸다. 설명을 바꾸면 임베딩 점수가 같이 바뀐다.
* **이 24개 질의는 설명을 한 번 조정하는 데 쓰였으므로 두 번째 표는 순수한 held-out 이 아니다.** 한 번씩만 돌렸고 표본이 작다.
* 지연은 서버를 다른 세션과 나눠 쓰는 상태에서 잰 값이고 동시 3개로 돌렸다. LLM 방식은 1단계 한 번 + 선택된 조사원마다 2단계 한 번씩이라 질의 하나에 수 분이 걸릴 수 있다.

### 질문에 대한 결론

* **LLM 라우팅이 필수는 아니다.** 임베딩 + 최소 유사도는 거의 같은 정확도(22/24 vs 24/24)를 1~2초에 낸다. LLM 은 「없음」 판정을 더 잘하지만 느리고 지연이 예측 불가(2.5~208초)이며 호출이 질의마다 여러 번 든다.
* 기존 측정 48개 질의에서 임베딩 1위 점수가 [0.65, 0.70) 인 애매한 질의는 15개(31%)이고, 그 밖은 임베딩 단독 확정 오류가 0건이었다. 따라서 **하이브리드(애매한 구간만 LLM 에 묻기)** 가 합리적인 다음 단계로 보이나 **구현하지 않았고 이 추정은 검증되지 않았다**(기준값을 정한 같은 데이터로 센 값).

| SSE `GET /runs/31/events` | 접속 즉시 현재 상태 → +11초 증강 후 답변 도착(66초 소요) → +58초 증강 전 답변 도착(113초 소요) → `ok/done` → 서버가 스트림을 닫음(이벤트 4개), 전체 실행 115초 |

## 5. 검증하지 못한 것

* MCP 가 빈 결과(`content: []`)를 돌려줄 때 실제 MCP 클라이언트(예: Claude Code)가 어떻게 처리하는지는 확인하지 않았다(`tools/call` 응답 구조만 확인).
* SSE 연결이 끊겼다가 폴링으로 대체되는 경로는 브라우저에서 강제로 끊어 시험하지 않았다(코드로만 존재).
* 서버가 프로세스 여럿이면 SSE 방송이 동작하지 않는다(프로세스 메모리). 지금은 프로세스 하나다.
* 비동기 실행의 취소 기능은 없다. 실행 중에 만들어진 작업이 많아도 동시 실행 개수 제한이 없다.
* 프로시저 단계의 최소 유사도(기본 0)는 보정하지 않았다.
* 하이브리드 라우팅은 구현하지 않았다.
* ko 외 언어 화면 렌더링은 확인하지 않았다(키 집합 일치만 `check-i18n`).
