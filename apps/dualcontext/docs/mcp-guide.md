# MCP 사용 가이드 (제로 컨텍스트용)

이 파일만 읽고 `dualcontext` MCP 서버를 쓸 수 있게 쓴 문서다. 구현 세부는 `architecture.md` · `internals.md`, 계약은 `api.md`.

## 한 줄 요약

질의를 주면 **그 질의에 답할 때 쓸 배경 컨텍스트(텍스트)** 를 돌려주는 MCP 서버다. **답변은 돌려주지 않는다.** 답은 호출한 쪽 모델이 그 컨텍스트를 읽고 직접 쓴다.

## 계약 요약

도구 `augment_context(query, effort?)` 하나. 응답은 고정 머리 + 컨텍스트. 정확한 계약은 `api.md`, 설계 배경은 `mcp-design.md`. 도구 목록(`tools/list`)의 입력 스키마에 `effort` 가 없으면 구버전 서버다: 그 경우 `query` 만 주고, 응답은 머리 없는 컨텍스트 텍스트(또는 빈 응답)다.

## 이 서비스가 무엇인가

「확장된 Dual RAG」다. 질의가 오면 서버가 다음을 한다.

1. **조사원 고르기**: 출처마다 하나인 조사원 중 질의에 맞는 상위 몇 개를 고른다.
2. **수집**: 고른 조사원이 자기 출처에서 원재료를 모은다.
3. **프로시저 고르기**: 조사원에 연결된 「분석 절차 · 추출 기준」을 고른다.
4. **라이터**: (조사원 자료, 프로시저) 쌍으로 컨텍스트 텍스트를 만든다.

조사원 종류(`src/server/collect/`): 웹 검색(DuckDuckGo), pgvector 테이블 벡터 검색, 볼륨 폴더(텍스트 파일), 사이트 크롤러(별도 컨테이너), 코드베이스(Git 레포 심볼 · 호출 구조). 어떤 조사원이 켜져 있는지는 관리자 사이트 「조사원」 화면에서 본다(배포마다 다르다).

## 언제 부르나

| 부른다 | 부르지 않는다 |
| --- | --- |
| 전문 · 비공개 · 최신 자료가 필요한 질문(등록된 데이터셋 · 코드베이스 · 크롤한 사이트 관련) | 일반 상식 · 잡담 · 번역 · 서버에 자료가 없을 주제 |
| 수치 · 사양 · 문서 내용 같은 **사실 확인** | 이미 이 대화에 근거 자료가 있는 질문 |

한 번 부르면 수십 초~수 분이 걸릴 수 있다(LLM 호출이 라우팅 · 라이터에 들어간다. LLM 호출 하나 중앙값 16.7초: `internals.md`). 같은 질의를 반복해 부르지 않는다.

## 연결 (현재)

서버는 Docker 컨테이너 `dualcontext` 하나다. 클라이언트가 컨테이너 안에서 stdio 프로세스를 띄우고, 그 프로세스는 같은 컨테이너의 서버(내부 listener)로 중계한다. 서버가 떠 있지 않으면 호출이 `dualcontext server is not reachable` 오류가 된다.

```json
{
  "mcpServers": {
    "dualcontext": {
      "command": "docker",
      "args": ["exec", "-i", "dualcontext", "node", "/app/dist/server/index.js", "--stdio"]
    }
  }
}
```

* 컨테이너가 떠 있어야 한다(`docker ps` 에 `dualcontext`). 없으면 저장소 루트에서 `npm run deploy dualcontext`.
* 헬스: `curl http://127.0.0.1:18081/health` → `200 {"status":"ok",...}`(포트는 `DUALCONTEXT_HOST_PORT`, 기본 18081). 503 이면 DB 가 안 된다.
* stdout 은 프로토콜 전용이다. 서버 로그는 stderr 로 나간다.
* 임베딩 · LLM 서버가 필요하다(관리자 「AI 서버 설정」). 꺼져 있으면 호출이 오류가 되거나 라우팅이 약해진다.

## 호출과 응답

```
augment_context(query: string, effort?: "light" | "middle" | "high" | "xhigh")   // effort 기본 light
→ content: [{ type:"text", text:"<고정 머리>
---
<컨텍스트>" }]
```

* `query` 는 **정보 필요**를 사용자의 말 그대로 쓴다. 이름 · 숫자 · 전문 용어는 원문 그대로 두고, 키워드만 늘어놓지 않는다(한국어 질문에 든 영문 이름으로 영문 자료가 검색된 사례가 있다: F1 보고서).
* 한 번의 호출은 **정보 필요 하나**를 맡는다. 한 질문이 여러 필요를 가지면 필요마다 부를 수 있다. 같은 필요를 같은 `effort` 에서 질의만 바꿔 되풀이하지 않는다 — 컨텍스트가 얇으면 `effort` 를 올려 다시 부르거나, 가진 것으로 답하고 부족한 점을 밝힌다.

응답 머리: `[dualcontext] effort=… coverage=ok|partial|none sources=N [reflections=N] elapsed=Ns`, 다음 줄 `next: …`.

| 응답 | 뜻 | 할 일 |
| --- | --- | --- |
| `coverage=ok` | 컨텍스트가 만들어졌다 | 읽고 **근거로 삼아** 직접 답한다 |
| `coverage=partial` | 평가가 통과하지 못한 채 멈췄다(`high`·`xhigh` 만). `missing:` 줄이 부족한 컨텍스트다 | 가진 것으로 답하되 `missing:` 를 한계로 밝힌다. `next: effort=xhigh` 가 있으면 한 번 올려 다시 부를 수 있다 |
| `coverage=none` | 마땅한 조사원이 없다 = 자료를 공급하지 않는다 | **그 필요는 재시도하지 않는다.** 자기 지식으로 답하고 근거 자료가 없었음을 밝힌다 |
| `isError` | 질의 분석 실패 등(빈 결과로 숨기지 않는다) | 같은 오류면 자료 없이 답한다. 머리의 `next:` 를 따른다 |

## effort: 어느 수준의 정보를 받는가

> **경고: `middle` 이상은 장기 실행이다.** 측정(공유 모델 서버, 같은 질의): `light` 16~28초, `middle` 20분~76분(두 번 측정에서 크게 달랐다), `high` 약 81분(평가는 1번에 통과했는데도 — 시간 대부분이 질의 분해 · 아이템 빌드). 대부분의 MCP 클라이언트는 1분쯤 기다리다 시간 초과를 보고한다(SDK 기본 요청 제한 60초). **클라이언트가 취소 알림을 보내거나 연결을 끊으면 서버가 그 실행을 취소하므로** 시간 초과된 `middle` 이상 호출은 결과를 남기지 않는다(진행 알림으로 제한을 연장하는 클라이언트(`onprogress` + `resetTimeoutOnProgress`)는 계속 기다릴 수 있다). 사용자가 긴 대기를 받아들인 경우에만 `middle` 이상을 쓰고, 아니면 `light` 로 하고 부족한 점을 밝힌다. 위 수치는 단일 측정이라 환경에 따라 다르다.

`effort` 는 **이 질의에 대해 서버가 어느 수준의 정보를 만들어 주는가**다. 답에 필요한 수준을 골라 쓴다. 단계가 올라갈수록 더 꼼꼼하고 느리다. 정하는 인자는 이 하나뿐이고, 분해 · 리플렉션 횟수를 직접 지정하는 인자는 없으며 서버가 단계를 자동으로 올리지도 않는다.

| effort | 받는 정보 수준 | 서버가 하는 일 |
| --- | --- | --- |
| `light` (기본) | 질의가 **말 그대로 묻는 것**에 대한 정보 | 질의 분해 없이 한 번 증강(classic) |
| `middle` | 질의에 **숨은 복합 정보**까지: 질의가 함축하지만 적지 않은 하위 필요 | 질의를 나눠 아이템별로 컨텍스트를 만들어 합침(decompose) |
| `high` | 질의에 **적합한지 내부에서 검증한** 정보: 모은 것의 빈틈을 찾아 채운 뒤 제공 | `middle` + 모은 컨텍스트로 답을 만들어 평가하고 보강, 리플렉션 최대 2번 |
| `xhigh` | `high` 보다 **강화된 검증 · 고도화된** 정보 | `high` 와 같되 리플렉션 최대 4번. 가장 느리다 |

* 모르면 `light` 로 시작한다. `high` 응답이 `next: effort=xhigh`(검증을 다 못 마쳤다는 뜻)면 한 번 올려 다시 부를 수 있다.
* 높은 단계일수록 느리다(`light` 수 초~수십 초, `middle` 이상은 수십 분~한 시간 넘게. 위 경고).
* 서버 안에서 만든 답변 · 평가는 응답에 담기지 않는다 — 응답은 컨텍스트뿐이다.

## 컨텍스트 읽는 법

본문은 마크다운이다. 섹션 구조:

* `## 조사원: <이름>` … 조사원별 자료와 적용된 프로시저(절차 · 출력 형식).
* `## 웹 검색 결과(검증되지 않은 보조 자료)` … 웹 검색 조사원 자료는 **따로 뒤에** 온다. 조사원 자료와 어긋나면 조사원 자료를 우선하고, 질문과 무관하면 쓰지 않는다.
* `## 사전 제공된 컨텍스트` … 계획 모드에서만. 질의를 쪼갠 선행 항목의 컨텍스트이며, 배경 지식으로만 쓴다.

## 알려진 한계 (근거: `seed-data/domains/_experiments/` 보고서)

* **자료가 있어도 놓칠 수 있다.** 행은 검색됐는데 전달된 발췌가 짧게 잘려 정답 문장이 빠진 사례, 아예 검색되지 않은 사례가 있었다(F1 · F2 · F3). 컨텍스트에 없다고 해서 서버 자료 전체에 없다는 뜻이 아니다 — 「제공된 컨텍스트에는 없다」로 한정해 말한다.
* **무관한 자료가 섞일 수 있다.** 범위 밖 질문에서도 후보를 채워 무관한 조사원 자료가 들어온 사례가 있다(F3-4). 질문과 관련 없는 섹션은 무시한다.
* **컨텍스트에 없는 해석을 덧붙이지 않는다.** 단위가 적히지 않은 값을 단정하는 식의 답변 오류가 실험에서 관찰됐다(F1 · F3). 자료가 보장하는 범위 안에서만 말한다.
* 표본이 작고 채점이 모델이었으므로 위 항목은 경향이지 보장이 아니다.

## 데이터 · 보안 주의

* 웹 검색 조사원이 고르면 질의에서 만든 검색어가 DuckDuckGo 로 나간다. 질의는 라우팅 · 라이터용 LLM 서버로도 간다. **비밀 · 개인정보를 질의에 넣지 않는다.**
* MCP 호출은 서버의 「실행 로그」에 `MCP` 뱃지가 붙어 **남는다**(질의 원문이 평문으로 쌓인다, `constraints.md`). 관리자 사이트에서 이 호출이 어떻게 처리됐는지(라우팅 · 자료 · 컨텍스트) 볼 수 있다.
* 관리자 사이트(`http://127.0.0.1:18081/`)는 인증이 없어 루프백으로만 열려 있다. 질의 시험은 거기 「시험 실행」에서 할 수 있다.

## 문제 해결

| 증상 | 원인 후보 | 확인 |
| --- | --- | --- |
| 연결 실패 | 컨테이너 없음 · 이름 다름 | `docker ps`, 이름은 `dualcontext`(`docker-compose.yml`) |
| 항상 `coverage=none` | 켜진 조사원이 없거나 라우팅이 아무것도 못 고름 | 관리자 「조사원」 화면, 「라우팅 미리보기」 |
| 매우 느림 · 오류 | AI 서버(LLM · 임베딩) 지연 · 다운 | 관리자 「AI 서버 설정」, `/api/admin/status` |
| 호출이 느림 · 시간 초과 | `effort` 가 `middle` 이상(수십 분)이거나 AI 서버 지연. 시간 초과 뒤에도 서버 작업은 계속된다 | 응답 머리의 `effort` · `elapsed`, 관리자 실행 로그의 `MCP` 항목 |
