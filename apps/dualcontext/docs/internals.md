# 내부 결정

코드만으로는 드러나지 않는 결정들이다.

* **도구가 하나인 이유.** 호출자는 질의만 안다. 어떤 조사원 · 프로시저를 쓸지는 서버 내부의 라우팅이 정한다.
* **연결은 조사원이 소유한다.** 프로시저는 독립이고 `researcher_procedures` 가 연결(순서 포함)을 가진다. 같은 프로시저(예: 「근거 신뢰도 점검」)를 여러 조사원이 공유한다. 첫 스키마(프로시저가 조사원에 속함)에서는 시작 시 SQL 이 기존 연결을 옮기고 열을 지운다.
* **코드 식별자는 researcher, 화면 명칭은 조사원.** 정식 명칭만 바꾸고 식별자는 이론의 영어 용어(Researcher)를 유지했다.
* **라우팅은 두 단계이고 상위 개수가 각각 있다.** 조사원 상위 N, 그 조사원의 연결 프로시저 상위 M. 결과는 쌍(조사원, 프로시저)의 목록이고, 같은 자료에 프로시저가 여럿이면 쌍이 여럿이다.
* **라이터 호출 방식은 설정이다.** 일괄은 모든 쌍을 한 번에 받아 쌍 사이 모순까지 다룰 수 있고, 쌍별은 쌍마다 호출해 이어 붙이므로 개별 컨텍스트는 잘 만들지만 쌍 사이 모순은 풀지 못한다.
* **2단계 벡터 검색.** MRL 축소 컬럼의 HNSW 로 후보 topK×8 을 뽑고 전체 차원 컬럼으로 재순위화한다. 인덱스는 축소 컬럼에만 건다(요구). 질의 벡터도 같은 방식으로 앞 N개를 자르고 재정규화한다.
* **MRL 축소는 앞 N개 자르기다.** 모델이 Matryoshka 학습된 경우에만 의미가 있다. 서버(`reduceMrl`)와 적재 스크립트가 같은 계산을 쓴다.
* **추론 모델은 `max_tokens` 를 제한하지 않는다.** `reasoning_content` 를 먼저 길게 내므로 제한하면 `content` 가 비어 온다. 비어 오면 오류로 올려 되돌림 경로가 드러나게 한다.
* **프리셋은 한 번만.** `seed_state` 표식으로 일회성이라 관리자가 지운 프리셋이 재시작에 되살아나지 않는다. 기본 라우터 · 라이터 · AI 서버 행은 `ON CONFLICT DO NOTHING` 이라 관리자가 고친 값을 덮어쓰지 않는다.
* **실행 로그는 설정 스냅샷을 함께 남긴다.** 라우터 · 라이터(프롬프트 포함) · 모델 이름이 나중에 바뀌어도 그 실행이 왜 그 결과였는지 로그만으로 알 수 있어야 하기 때문이다. API 키는 스냅샷에서 제외한다.
* **증강의 효과는 같은 모델 · 같은 조건의 두 답변으로 본다.** 시험 실행은 컨텍스트를 만든 뒤 `qwen36-35b` 같은 채팅 모델로 최종 답변을 두 번 만든다. 증강 전은 질의만, 증강 후는 질의 + 컨텍스트이고 프롬프트의 다른 점은 컨텍스트 유무뿐이다(`src/server/answer`). 두 호출은 병렬이다. 프롬프트는 코드 상수이며 로그의 설정 스냅샷에 그대로 남는다(화면에서 편집하게 하는 것은 아직 없다).
* **답변이 실패해도 실행은 성공이다.** 답변별로 `{ text:null, error }` 를 로그에 남기고 화면에 이유를 보인다. MCP 도구는 답변을 만들지 않는다(호출한 쪽의 LLM 이 컨텍스트로 답한다).
* **시험 실행은 비동기다.** 한 HTTP 요청에 수 분을 묶지 않으려고 `POST /augment` 는 `running` 행을 만들고 즉시 202 를 돌려주며 작업은 프로세스 안에서 이어진다(`admin/runs`). 단계마다 행을 고치고 `EventEmitter` 로 방송하며, SSE 는 그 방송을, 폴링은 같은 행을 읽는다. 화면 훅(`front/lib/run.ts`)은 SSE 를 쓰다가 끊기면 폴링으로 바꾼다. 방송은 프로세스 메모리라 서버는 프로세스 하나여야 하고, 서버가 재시작되면 `running` 으로 남은 행을 오류(「서버가 다시 시작되어 실행이 중단되었다」)로 닫는다. 이 정리는 서버 프로세스에서만 하고 MCP stdio 프로세스에서는 하지 않는다(서버의 진행 중 작업을 잘못 닫기 때문). 취소 기능은 없다.
* **「마땅한 조사원 없음」은 판정이고, 그 결과는 빈 컨텍스트다.** 임베딩 라우팅은 최소 유사도(기본 0.67)에 못 미치는 후보를 상위 N 안이어도 제외하고, 키워드 방식은 맞는 키워드가 없으면 선택하지 않으며, LLM 방식은 `[]` 로 답할 수 있다. 선택이 0개면 컨텍스트는 빈 문자열이고 라이터를 부르지 않으며 MCP 는 빈 결과를 돌려준다. 시험 실행은 증강 후 답변을 만들지 않는다(컨텍스트가 없으면 증강 전 답변과 같은 입력이다). 라우터 점수표(후보별 유사도와 선택 여부)를 실행 로그에 남겨 왜 그렇게 판정했는지 읽을 수 있다.
* **최소 유사도 0.67 은 측정으로 정했다.** 기대 조사원이 있는 질의 23개 vs 무관·범위 밖 25개에서 1위 점수의 AUC 가 0.988 로, 격차 기반 규칙(0.90 · 0.85)이나 조사원별 표준화(0.98)보다 높거나 같았다. 0.67 에서 무관 질의 25개 중 22개가 「없음」, 정상 질의 오판 1개, 기대 (질의, 조사원) 쌍 36개 중 31개 유지(결과: `routing-calibration_result.json`). 한계: 점수가 0.5~0.85 에 압축돼 있어 하나의 기준값으로 완벽히 가를 수 없다(스크립트: `test/20261113/routing-calibration.mjs`)).
* **웹 검색 조사원은 설명이 곧 정책이다.** 설명이 「내부 자료에 없는 일반 사실을 웹에서」였을 때 LLM 라우팅은 무관한 질의 12개 중 11개에서 웹 검색을 골랐다(논리적으로 맞는 판단). 시점 민감 정보 전용으로 좁히니 12개 모두 「없음」이 됐다. 만능 폴백으로 둘지 전용으로 둘지는 제품 정책이다.
* **LLM 방식 vs 임베딩+최소유사도(새 질의 24개, 설명 조정 후).** 정확도 LLM 24/24, 임베딩 22/24. 지연은 LLM 호출 하나가 2.5~207.8초(중앙값 16.7초, 서버를 나눠 쓰는 상태), 임베딩은 1~2초. LLM 방식은 1단계 한 번 + 선택된 조사원마다 2단계 한 번씩 더 불러 한 질의에 수 분이 걸릴 수 있다. 하이브리드(임베딩 1위 점수가 [0.65, 0.70) 인 애매한 질의만 LLM 에 묻기)는 기존 측정 48개 질의 중 15개(31%)만 LLM 을 쓰면서 임베딩 단독 확정 오류가 0건이라고 추정되나 구현하지 않았다.
* **컨텍스트는 명령이 아니라 참고 자료다.** 실행 로그 29건을 건별로 분석한 결과(`test/20261114/dualcontext-per-run-analysis_report.md`), 이전 답변 프롬프트의 「컨텍스트를 근거로 답하라. 컨텍스트에 없는 내용은 추측하지 말고 부족하다고 밝혀라」가 무관한 자료가 붙은 질의에서 모델이 아는 답까지 거절하게 했다(#16 GIMP 절차 · #27 빵 반죽 · #29). 관련 자료가 붙은 건에서는 같은 문구가 환각을 바로잡는 데 도움이 됐으므로, 문구를 없애는 것이 아니라 「자료는 참고, 일반 지식으로 보완, 자료 출처만 번호로 표시, 없는 출처 · URL 은 만들지 않는다」로 바꿨다. 라이터는 자료를 조사원별로 한 번만 싣고(예전에는 프로시저마다 같은 자료를 반복해 컨텍스트가 두 배 가까이 길었다), 프로시저는 「분석 관점(제안)」으로 쓰며, 자료에 `R<조사원id>-<순번>` 번호와 유사도를 붙인다.
* **웹 검색 자료는 컨텍스트에서 따로 다룬다.** 웹 조각은 점수가 없고 출처 신뢰도와 최신성이 균일하지 않아 큐레이션 자료와 섞이면 모델이 비중을 가리기 어렵다. 그래서 웹 쌍은 큐레이션 쌍 뒤에 두고(템플릿 라이터는 별도 섹션, LLM 라이터는 쌍 머리의 성격 표시), 「조사원 자료와 어긋나면 조사원 자료를 우선, 질문과 무관하면 쓰지 않는다」를 밝힌다. 이 표시가 있으면 웹 조사원을 느슨하게 포함시켜도 잡음 부담이 줄어들 것이라는 가설에서 한 변경이며, 증강 전후 답변 품질로 검증한 것은 아니다. 실행 로그의 `pairs` 순서는 라우팅 순서 그대로다(라이터 입력만 정렬한다).
* **「부족한 항목: 없음」은 거짓이었다.** 이전 라이터는 수집 오류 · 빈 결과만 검사해, 질의와 무관한 자료만 모였어도 「없음」이라고 적었다(로그 30건 모두 「없음」으로 끝났고, 건별 분석 보고 중 18건이 자료가 빠졌거나 무관한데도 그렇다고 짚었다). 지금은 실제로 자료가 없거나 수집이 실패한 조사원이 있을 때만 「찾지 못한 것」을 쓴다.
* **조사원 라우팅이 맞아도 행이 무관할 수 있어, 자료 단위 관련도 기준(`minScore` 0.72)을 둔다.** 조사원 라우팅은 설명 문구와 질의의 유사도만 보므로(`#36`: 소프트웨어 개발 0.6856) 조사원 선택이 맞아 보여도 실제 행은 SO 질문이었다. 행 유사도는 관련 20건 최저 0.7524 · 부분 12건 최저 0.7332 · 무관 36건 중 25건이 0.72 미만이라 분리가 훨씬 낫다(`test/20261113/material-relevance.mjs`). 한계: 라벨은 서브에이전트 판정이라 미검증이고, 같은 조사원 안의 근접 도메인(금융 vs 산업 뉴스 같은 합성 뉴스)은 0.72 를 넘는다.
* **복합 질의는 하위 질문으로도 라우팅한다(`splitQuery`).** 문장 끝과 요청·의문 어미 뒤 쉼표에서 나눠(12자 미만 조각은 이웃에 붙임, 최대 4개) 통째 질의와 하위 질문마다 라우팅하고 합집합을 고른다. 하위 질문은 상위 1개만 고르고, 그 조사원은 그 하위 질문으로 수집한다. 통째 질의가 고른 조사원은 통째 질의로만 수집한다. 근거: 조사원 27개에서 하위 질문마다 상위 3개를 고르면 #8 이 8개를 골랐다. 측정(복합 질의 8개, `routing-calibration27_result.json`): 하위 질문 상위 1개 규칙에서 기대 조사원 재현율 0.938, 둘 다 맞힌 것 7/8, 평균 2.13개 선택.
* **조사원 라우팅은 최고 점수와의 상대 마진(0.05)도 쓴다.** 임계값만으로는 무관 질의가 0.60~0.76 점수를 받아 분리되지 않는다(0.67 에서 무관 12개 중 6개만 아무것도 안 고름, 0.72 로 올리면 단일 질의 재현율이 0.611 로 떨어짐). 마진 0.05 는 단일 질의 재현율 0.926 을 지키면서 평균 선택 수를 1.72 → 1.33 으로 줄였다. 1위 정확도는 54개 중 51개였다. 상수(`researcherMargin`)라 관리자 화면에서 바꿀 수 없다.
* **식별자는 문자열로 정확히 찾는다(`identifiers.ts`).** 임베딩이 못 가르는 CVE ID · 영문 모델명 · 영문 약어 · 「질문 61」 번호를 질의에서 뽑아 본문/제목을 `ilike` 로 찾고, 5행을 넘게 걸리는 흔한 표기는 버린다. 일치 행은 벡터 결과 앞에 `질의에 적힌 표기와 일치` 표시와 함께 붙고 `minScore` 를 면제받는다. 효과: 실행 로그 #25 의 질의 CVE 3건이 컨텍스트 본문에 0건 → 3건 모두(`e2e-context_result.json`). 일치 행 중 일부(CVE-2010-2871 · CVE-2010-3912)는 질의에 없던 CVE 라 본문이 다른 표기와 겹쳐 걸린 것으로 보이며 원인은 확인하지 않았다.
* **일상 Q&A 분야는 자료 기준을 0.76 으로 올렸다.** 일상 질문들은 서로 의미가 가까워 0.72 에서는 무관 질의에도 행이 붙었다. 측정(`row-score-everyday_result.json`): 0.72 는 맞는 질의 17/17 유지·무관 12개 중 5개 빈 결과, 0.76 은 14/17 · 9/12. 종단 재측정에서 무관 질의 12개 중 빈 컨텍스트가 8개 → 10개(`e2e-context_result.json`). 같은 질의로 정한 값이라 과적합 위험이 있다.
* **자료가 없는 조사원에는 프로시저를 고르지 않는다.** 관련 없는 절차(육아 질의에 「해결 대안과 호환성 비교」)가 컨텍스트에 실리는 일을 막는다.
* **LLM 호출의 300초 끊김은 undici 의 `headersTimeout` 이었다.** 추론 모델은 스트리밍 없이 답을 다 만든 뒤에야 응답 헤더를 보내서, `AbortSignal` 을 늘려도 Node 내장 `fetch` 가 기본 300초에 `fetch failed`(`UND_ERR_HEADERS_TIMEOUT`)로 끊었다. 호출 전용 `undici` `Agent`(`headersTimeout`·`bodyTimeout` 900초)와 undici 의 `fetch` 로 해결했다. 재현 프로브 `test/20261113/slow-header-probe.mjs`: 수정 전 306.7초 실패, 수정 후 320.0초 정상.
* **컨텍스트에 싣는 자료 길이는 조사원 설정(`snippetChars`, 기본 1200)이다.** 600자로 자르던 때는 검색이 맞아도 정답 문장이 잘려 사라졌다. 고정된 실험 질의 3묶음(F1·F2·F3)의 정답 인용문이 컨텍스트에 포함된 사실이 47개 중 25 → 31개로 늘었다(`test/20261113/evidence-recheck.mjs`).
* **로그는 실패도 남긴다.** 실행이 던지면 `status=error` 와 이유를 기록하고 `502` 로 응답한다. 라우팅 방법이 실패해 키워드로 되돌아간 경우나 수집이 실패한 경우는 실행 자체는 성공이므로 `status=ok` 이고, 그 사실은 `researcherRouting` · 쌍의 `procedureRouting` · 쌍의 `error` 에 남는다. 설정 스냅샷을 읽는 단계가 실패하면(DB 장애) 로그도 남기지 못한다.
* **MCP 호출은 로그에 남기지 않는다.** 요청이 시험 실행의 로그였고, MCP 질의 원문을 평문으로 쌓는 것은 별도 결정이 필요하다. 필요하면 `augment_runs` 에 `source` 열을 더해 같은 경로로 남길 수 있다.
* **전문 검색 질의를 AND 에서 OR 로 바꾼다.** 폴더 조사원에서 `plainto_tsquery` 의 `&` 를 `|` 로 치환하고 `ts_rank` 로 정렬한다.
* **초기화 SQL 은 매 시작마다 돈다.** 모든 문장이 멱등이다. 마이그레이션 도구는 아직 없다.
* **엔트리포인트는 `wait -n` 으로 두 프로세스를 감시한다.** 하나가 죽으면 나머지를 내리고 종료 코드를 그대로 낸다.
* **`dist` 는 번들 하나다.** 런타임 이미지에 npm 이 필요 없다. Node 바이너리만 `node:26-bookworm-slim` 에서 복사하고 `libatomic1` 을 apt 로 둔다.

## 라우팅 단계 구성 결정

* 조사원 선택 기본값은 임베딩(상위 6, 최소 0.6) → LLM(「없음」 허용) 두 단계, 질의 분해 없음. 임베딩은 후보 추출(넓힌 후보 재현율 0.99~1.0), LLM 은 선택·거절을 맡는다.
* 근거와 한계: `test/20261115/route-eval_report.md`(136개, 라벨은 자체 작성, heldout 30개). LLM 만/분해(규칙·LLM)는 이득 없이 느려 기본으로 쓰지 않는다.
* LLM 단계는 비결정적(같은 질의 126/136 동일 선택)이고 질의당 p50 약 4초가 든다. 단계의 `onError: skip` 이면 LLM 실패 시 넓은 후보가 그대로 남으므로 `mode`/`steps` 기록을 확인한다.
* 저장된 설정은 배포로 바뀌지 않는다. 기본값 변경은 새 설치에만 적용된다.

## 웹 검색 조사원의 프로시저

* 웹 검색은 특정 분야가 아니라 공개 정보 전반을 보완하는 출처이므로, 연결 프로시저도 분야가 아니라 **질의 유형(목적)** 으로 나눈다: 최신 동향 · 사실 확인 · 시세 · 일정 · 제품 비교 · 후기 · 방법 · 장소 · 규정 · 개념 · 기술 해결 · 조언 · 건강 · 인물 · 쟁점 · 실시간 현황(`seed/presets/procedures.ts`, `[웹]` 접두).
* 이름에 `[웹]` 이 붙은 프로시저는 시드 프리셋이라 새 설치에만 들어간다. 이미 돌고 있는 서버에는 관리자 화면(또는 API)에서 만들고 웹 조사원에 연결해야 한다.
* 프로시저가 늘면 둘째 자리 노이즈가 문제다(`test/20261115/web-procedure_report.md`): 프로시저 단계가 margin 1 로 항상 상위 2개를 채우면 무관한 프로시저가 따라 붙는다. margin 은 전역 설정이라 다른 조사원에도 영향을 주므로 기본값은 바꾸지 않았다(측정은 margin 0.03 에서 상위 2개 적중 유지, 기대 밖 선택 0.97→0.35).

## 기본 프로시저(폴백) 결정

* 배경: 조사원이 골라지고 자료도 모였는데 프로시저 라우팅이 0개를 고르면 프로시저 없는 쌍(`조사원 / -`)이 되어 분석 관점이 하나도 안 붙은 채 버려졌다(임베딩 최소 유사도 · LLM 「없음」이 흔하다).
* 그래서 조사원에 `defaultProcedureId`(`researchers.default_procedure_id`, 기본 `null`)를 둔다. `augmentQuery` 는 **라우팅이 0개를 고른 경우에만**, 그 id 가 이 조사원의 연결 목록에 있고 **활성**이면 그 프로시저로 쌍을 만든다. 하나라도 골랐으면 붙이지 않는다(라우팅 결과를 덮지 않는다). 기본이 없거나 비활성이거나 연결 목록에 없으면 이전 동작(프로시저 없는 쌍)이다.
* 자료가 없어 `skipped(no-material)` 인 조사원에는 붙이지 않는다. 쌍이 프로시저를 얻어도 자료가 없으면 관련 없는 절차만 컨텍스트에 실리기 때문이다. 이때 프로시저 라우팅 호출도 하지 않는다.
* 표기: 폴백으로 붙은 쌍의 `procedureRouting` 은 라우터 모드 대신 **`default`** 다(`skipped(no-material)` 처럼 모드가 아닌 값 한 가지). 실행 로그의 `routing.procedures[]` 항목에는 `fallback: "default"` 가 붙고, 라우팅 탭이 한 줄로 알린다(`run-procedure-fallback`). 후보 점수(`candidates`)는 라우팅이 매긴 그대로 남아 「점수상 아무것도 고르지 않았다」는 사실도 같이 읽힌다.
* 검증은 저장 시점에 한다: 기본 프로시저는 같은 요청의 `procedureIds` 안이어야 하고 아니면 `400`. 연결 해제와 기본의 모순은 자동으로 풀지 않고 거절한다(화면은 연결을 해제하면 기본 선택도 지워 이 400 이 나지 않게 한다). DB 는 `ON DELETE SET NULL` 외래키라 프로시저 삭제 시 기본이 `null` 이 되고, 연결 행만 다른 경로로 사라져도 `augmentQuery` 가 연결 목록에서 찾으므로 붙지 않는다.
* 마이그레이션 `docker/initdb/006_researcher_default_procedure.sql` 은 멱등이다(열 `ADD COLUMN IF NOT EXISTS`, 외래키는 없을 때만 추가). 기존 조사원은 모두 `null` 이라 동작이 바뀌지 않는다.

## 개별 라우터 결정

* 배경: 웹 검색 조사원의 임베딩 점수가 거의 모든 질의에서 0.60~0.71 의 좁은 띠에 몰려(최신성이 필요한 질의와 아닌 질의의 최저·최고가 0.654 대 0.657), 절대 기준(0.67)과 마진으로는 가를 수 없다. 임베딩은 질의의 주제 가까움만 재고 「최신 정보가 필요한가」라는 성질은 거의 재지 못한다(`test/20261115/web-researcher-probe.mjs`).
* 그래서 조사원마다 단계 파이프라인(`Researcher.router`)을 줄 수 있게 했다. 전역 파이프라인과 같은 실행기(`runPipeline`)에 후보를 그 조사원 하나로 넣는 것이므로 새 판정 코드는 없다. 개별 조사원은 전역 후보에서 빠지고(`routing/index.ts` 의 `selectResearchers`), 판정은 병렬이며 질의 임베딩은 한 번만 계산한다.
* 단계가 실패했을 때: `onError: skip`(기본)은 실패해도 **포함**(열림), `none` 은 **제외**(닫힘)다. 웹 검색처럼 빠뜨리는 비용이 큰 조사원은 열림, 잡음 비용이 큰 조사원은 닫힘으로 둔다.
* LLM 단계는 호출이 한 번 더 늘어난다(개별 라우터 조사원 수만큼). 동시 호출 제한(3건)이 걸려 있어 지연은 그만큼 늘 수 있다.
* 기본 설정으로 어떤 조사원에도 개별 라우터를 달지 않았다(데이터는 그대로). 효과는 측정 전이다.

## LLM 호출 제어 결정

* 채팅 호출은 총 시간이 아니라 **유휴 시간**으로 멈춤을 판단한다. 스트리밍으로 받아 바이트(추론 토큰 포함)가 계속 오면 기다리고, 180초간 하나도 안 오면 끊는다. 총 시간 상한 1시간은 안전장치다. 근거: 총 900초 타임아웃으로 끊긴 실행 98번의 프롬프트(2,440자)를 제한 없이 스트리밍으로 다시 보내니 365초에 정상 완료됐다(`test/20261115/probe-run98.mjs`). 타임아웃 실패의 원인은 「끝나지 않는 추론」이 아니라 한 서버를 나눠 쓰며 생긴 대기였다. (그 대기가 정확히 무엇이었는지는 확인하지 못했다.)
* 동시 호출은 프로세스당 3건으로 묶는다. 서버가 `503 no eligible backend has free capacity`(과부하)나 429 로 답하면 2·4·8초 백오프로 최대 4회 시도한다. 다른 오류는 재시도하지 않는다.
* 임베딩·모델 목록 호출은 종전대로 총 900초 제한이다.
* 값은 `model/index.ts` 의 `defaultChatControl` 이다(환경 변수 아님).
* 중단·빈 응답 오류 문구에 그때까지 받은 양이 붙는다(`reasoningChars=… contentChars=…`). 총 상한(1시간)에 걸린 호출이 계속 생각만 한 것인지, 서버가 keep-alive 만 보낸 것인지를 다음 실패에서 가리기 위해서다. keep-alive 주석(`: ...`)도 바이트로 세어 유휴 시간을 갱신하므로, 서버가 대기 중에 keep-alive 를 보내면 유휴 판정이 무력해질 수 있다(미확인).
* 실행 기록의 답변 `ms` 는 동시 호출 제한 대기를 포함한다. 15건 동시 측정에서 일부 값이 수천 초인 것은 생성 시간이 아니라 대기열 때문이다.
* 서버가 스트리밍을 지원하지 않아 JSON 으로 답하면 그대로 받는다. 스트림이 종료 표지 없이 닫히면 오류다.

### 동작

* 출처: `git`(서버 안에서 깊이 1 클론 후 `.git` 삭제, 인덱스에 필요한 소스 조각만 남기고 작업 트리는 지운다) 또는 볼륨 안 폴더. 클론한 코드는 읽기만 하고 실행하지 않는다.
* 인덱스: 파일 → 심볼(함수 · 메서드 · 클래스 · 인터페이스 · 타입 · enum · struct · trait · 문서 머리글), 심볼 → 심볼(본문의 `이름(` 호출 중 레포에 정의된 이름, 정의가 3곳을 넘는 이름과 3자 미만 이름은 제외), 파일 → 파일(import, 상대 경로 · 접미 경로 일치). 지원: TS/JS, Python, Go, Java, Kotlin/Scala, C#, Rust, C/C++, Ruby, PHP, Swift, 문서(md · rst · txt).
* 실행 위치: 인덱스 읽기 · 파싱 · 검색기 구축 · 검색은 검색 스레드(`workers/search`), 만들기의 스캔 · 심볼 · 그래프 · 파일 쓰기는 빌드 스레드(`workers/build`)에서 돈다. 메인은 `stat` 으로 존재만 알고 topK 자료만 받는다(아래 「CPU 격리 결정」).
* 질의: 영문 토큰(camelCase · snake_case 분해 + 원형)으로 심볼 이름(가중 4) · 경로(1.5) · 소스 조각(1)에 BM25 를 매기고, 상위 3×topK 심볼의 호출 이웃(호출하는 쪽 · 호출되는 쪽)에 점수의 35% 를 나눠 올려 구조상 가까운 심볼을 끌어올린다. 임베딩은 쓰지 않는다(AI 서버 없이 동작, 결정적).
* 자료: 제목 `경로:시작-끝줄 종류 이름`, 본문 = 소스 조각 + `calls:` · `called by:` · `file imports:` + (이웃으로 끌려온 경우) 출처 심볼. 점수는 붙이지 않는다(코사인이 아니므로 다른 조사원 점수와 섞이면 오해된다).
* 갱신: 인덱스가 없으면 첫 질의가 만들고 기다린다(`maxIndexSeconds`). 있으면 즉시 답하고 `refreshHours` 가 지났으면 뒤에서 다시 클론 · 인덱싱한다. 같은 키의 동시 만들기는 하나로 합치고, 실패하면 60초간 같은 오류를 돌려 클론을 되풀이하지 않는다(옛 인덱스가 있으면 계속 그것으로 답한다). 커밋 해시는 인덱스에 남기지만 변경 감지(`ls-remote` 비교)는 하지 않는다 — 주기마다 통째로 다시 만든다.
* 한계: 정규식 근사라 중괄호 · 들여쓰기가 흐트러진 코드나 동적 호출 · 데코레이터 · 매크로는 놓친다. 이름 일치라 `get`, `pop` 처럼 흔한 이름은 엉뚱한 정의로 이어질 수 있다(Flask 실측에서 확인). 심볼 끝 줄은 들여쓰기 기준 40줄 상한. 하나의 서버 프로세스 가정(인덱스 파일은 원자적으로 교체하지만 프로세스 간 락은 없다).
## 크롤러 조사원 결정

* 목적: 지정한 사이트(공개 문서·블로그)를 직접 크롤해 분석하는 조사원. 웹 검색 조사원과 달리 **정해진 출처**를 깊게 본다.
* 오픈소스 크롤러 비교. **직접 확인한 것은 Crawl4AI 뿐이다**(라이선스 Apache-2.0 은 저장소 API, 이미지는 도커 허브 `unclecode/crawl4ai:0.9.5` amd64 압축 2.3GB·풀면 5.7GB를 받아 실행, `/crawl`·토큰·SSRF 차단은 실제 호출). 다른 후보의 칸은 각 프로젝트의 알려진 사양에서 가져온 것으로 이번에 재확인하지 않았다.

| 후보 | 라이선스 | 자가호스팅 | LLM 친화 출력(마크다운) | JS 렌더링 | REST API | 이미지·부하 | 판정 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| **Crawl4AI** | Apache-2.0 | 공식 도커 이미지 1개(내장 Redis) | 기본 출력이 마크다운(가지치기 필터로 잡음 제거) | Chromium(Playwright) | `/crawl` 등 내장(FastAPI), 토큰 인증, 내장 SSRF 차단 | 압축 2.3GB, 실행 시 RAM 수 GB, shm 1GB | **채택** |
| Firecrawl(자가호스팅) | AGPL-3.0 | API + Redis + Playwright 서비스 여러 개 | 마크다운 | 예 | 예 | 컨테이너 여러 개, 일부 기능은 클라우드 전용 | AGPL(네트워크 사용 시 소스 공개 의무)과 다중 컨테이너로 제외 |

| Crawlee | Apache-2.0 | Node 라이브러리(서버 아님) | 없음(HTML) | Playwright/Puppeteer 크롤러 제공 | 없음(직접 작성) | Playwright 이미지 기반 | 서비스로 쓰려면 우리가 서버를 짜야 함. 이 저장소가 Node 라 잘 맞지만 마크다운 변환·REST 를 직접 만들게 된다 |
| Playwright 직접 | Apache-2.0 | 라이브러리 | 없음 | 예 | 없음 | 브라우저 포함 | 가장 가볍지만 추출·변환·큐를 전부 직접 구현 |

* 채택 이유: 마크다운 출력, JS 렌더링, REST API, 인증, SSRF 차단이 **이미 있는 유일한 Apache-2.0 이미지**다. 우리가 짜는 것은 정책(어디를 갈지)과 색인뿐이다. 단점은 이미지가 크고(5.7GB) 메모리를 쓴다는 것이다.
* 역할 분담: 크롤러 컨테이너는 URL 하나를 렌더링해 마크다운과 링크를 돌려주는 **부품**으로만 쓴다(Crawl4AI 자체의 깊은 크롤 기능은 쓰지 않는다). 깊이·도메인·robots·간격·SSRF·상한을 우리 쪽에서 결정해야 URL 마다 검사할 수 있고, 한도와 정책이 한 곳(`walk`)에 모이기 때문이다.
* 검색 방식: 기본안 그대로 **청크 + 임베딩 + 코사인 유사도**. 더 나은 설계를 찾지 못했다. 다만 두 가지를 더했다: (1) 페이지당 조각 수 상한(`perPage`)으로 한 페이지가 결과를 독점하지 않게 하고, (2) 조각 앞에 가장 가까운 제목을 붙여 임베딩한다. 임베딩은 `double precision[]` + 모델 이름으로 저장한다. 청크가 3000개로 묶여 있어 벡터 인덱스가 필요 없고, 임베딩 차원을 테이블에 고정하지 않는다(모델 교체 가능). 코사인은 처음에는 JS 메모리에서 계산했지만 DB 로 옮겼다: 행을 전부 읽어 3000×차원 배열을 JS 로 훑는 동기 CPU 가 이벤트 루프를 잡기 때문이다. 쿼리는 `embedding::vector <=> 질의` (pgvector 연산자만 쓰고 벡터 컬럼 · 인덱스는 만들지 않는다)이고 차원 조건이 캐스트보다 먼저 평가되도록 `materialized` CTE 안에 둔다. pgvector 컬럼·HNSW 는 청크가 수만 개로 늘 때 도입한다.
* 갱신: 캐시가 없으면 첫 질의가 크롤을 기다린다(최대 `maxCrawlSeconds`). 캐시가 있으면 즉시 답하고, 주기를 넘겼으면 백그라운드로 다시 크롤한다(stale-while-revalidate). 재크롤은 페이지 내용 해시가 같으면 청크와 임베딩을 그대로 둔다(임베딩 서버 호출 절약).
* 시드 프리셋은 넣지 않았다. 기본 데이터는 그대로다.
* 측정되지 않은 것: 임베딩 모델별 검색 품질, 대형 사이트(수백 페이지)에서의 크롤 시간, 한국어 사이트의 마크다운 품질, SPA 사이트(무한 스크롤·로그인 필요).

## CPU 격리 결정(수집기 영역)

설계 문서 `execution-design.md`(v5)의 「4. CPU 작업」 중 수집기 쪽 구현이다. 동기 CPU 작업이 이벤트 루프를 잡으면 취소 신호 · 시한 타이머 · 대기 큐가 돌지 못하므로, 크기 · 반복 상한이 있는 알고리즘으로 바꾸거나 종료 가능한 스레드로 옮겼다.

**선언한 동작 변경**

| 대상 | 변경 | 이유 |
| --- | --- | --- |
| robots 매칭 | 정규식 → 리터럴 조각 탐욕 배치. 경로 2048자 · 패턴 256자 · 선택 그룹 합친 규칙 200개 상한. 초과 Allow 패턴은 버리고 초과 Disallow 패턴은 앞 256자의 접두 규칙으로 줄인다 | 임의 패턴이 지수 시간 정규식이 된다(`/*a*a*a*a*b` + `a` 2000자). 옛 정규식과 6만 무작위 (패턴, 경로) 쌍에서 결과가 같음을 시험으로 고정(`robots.test.ts`). 복잡도는 O(경로 × 패턴 길이)로 **선형이 아니며** 상한으로 묶는다 |
| import 추출 | 파일 전체 `^\s*…` + `m` 정규식 → 줄 단위 스캐너. 4000자 초과 줄의 import 무시. 줄 사이를 `\s+` 로 넘던 형식은 `require(` · `import(` · `from` · 홀로 선 `import` 끝 줄 뒤 6줄과 Go 블록만 잇는다 | `\s*` 가 개행을 넘어 빈 줄이 많은 파일에서 이차 시간. 일반 형식(한 줄 · 위 다중 줄)은 옛 구현과 같은 결과임을 언어별 무작위 파일 1만 5천 개 비교로 확인. 문법 오류인 `from x`⏎`import y`(파이썬)는 더 이상 잡지 않는다 |
| 크롤러 제목 | 정규식 `^#{1,4}\s+(.+?)\s*#*$` → 비정규식 파서, 4000자 초과 줄은 제목이 아니라 본문 | 공백이 긴 줄에서 이차 시간. 8만 무작위 줄에서 옛 정규식과 같음(`#` 뒤가 공백뿐이면 마지막 공백 한 글자가 제목이 되는 경계까지) |
| 크롤러 코사인 | JS → DB. 차원이 다른 행 제외(옛 JS 는 앞 차원만 비교), NaN → 점수 0(옛 JS 는 전파), 동점은 `url, idx` 순서(옛 구현은 조회 순서 의존) | 동기 CPU 제거 · 결정적 순위. 정상 범위에서 JS 와 1e-5 이내로 같음을 실제 pgvector 로 확인(`sql.db.test.ts`) |
| 링크 필터 | include/exclude 정규식 판정이 `cpu.regex` 스레드로. 200ms 초과 묶음(링크 50개)은 전부 제외. 대상 2048자 초과 링크는 제외 | 임의 정규식(관리자 입력) 격리 |
| 색인 읽기 | 64MB 초과 파일은 읽지 않고 없는 것으로 본다. `hasIndex` 는 `stat` 만 한다 | 읽기 경로 상한 · 이중 파싱 제거 |
| 취소 | 요청 취소는 공유 작업(빌드 · 크롤 · 백필)을 죽이지 않고 기다림에서만 떨어진다. 취소는 조사원 실패 흡수 경계에서 삼키지 않는다 | 다른 요청이 같은 작업을 기다릴 수 있다 |
| 크롤 | 첫 실패 뒤 60초 백오프, 폴더 조사원 실행 단위 20MB 예산 | 실패 반복 · 폭주 방지 |

**잔여 문제(문서화만 한다)**: 임베딩 설정 고정은 호출 앞뒤 설정 비교라 A→B→A 변경은 못 잡는다. 키는 모델 이름뿐이라 endpoint 만 바뀌는 경우는 다시 임베딩되지 않는다. 라우팅 캐시 · 실행 질의 임베딩의 같은 경합은 이 영역 밖이다. 검색 스레드 `resourceLimits` 는 힙만 제한한다(RSS 는 계측). 폴더 조사원 시험의 파일 경로는 posix 규칙이라 윈도우 호스트에서는 컨테이너에서 돌려야 한다.

## 실행 로그 검색 결정

* **파생 열 + 트리거.** 필터 · 검색 · 쪽 나누기를 SQL 에서 하려고 `augment_runs` 에 `researcher_names` · `procedure_names`(pairs 에서 뽑은 이름, GIN 겹침 연산 `&&`)와 `search_tsv` 를 둔다. 이 열들은 `BEFORE INSERT OR UPDATE OF query, pairs, context, answers` 트리거(`005_runs_search.sql`)가 채운다. 갱신 쿼리마다 식을 따로 붙이는 대신 트리거를 고른 이유: 실행은 단계마다(pairs · context 한 번, answers 두 번) 행을 고치고 앞으로 쓰는 곳이 늘 수 있는데, 정의가 한 곳이어야 쓰는 쪽이 늘어도 어긋나지 않는다. 마지막 status · stage · duration 갱신은 이 열들을 지정하지 않아 트리거가 돌지 않는다. 옛 행 백필도 `UPDATE ... SET query = query WHERE search_tsv IS NULL` 로 같은 트리거를 태워 정의를 한 번만 쓴다. 단점: 트리거는 앱 코드에 보이지 않으므로 이 문서와 SQL 주석이 유일한 안내다.
* **한국어 FTS 설정은 `korean`(textsearch_ko).** 한국어 어절("얕은 클론", "예외 처리")은 형태소로 쪼개져 맞고, 영어 단어는 같은 설정 안에서 영어 어간으로 처리된다(`clones`·`clone`, `repositories`·`repository` 가 서로 맞는다). 영어용 설정을 따로 합치지 않았다. 대상 문서는 질의(가중치 A) + 최종 출력 `answers.after.text` · `answers.before.text`(B) + `context`(C)이고, 각 글은 20만 자로 자른다(tsvector 는 1MB 한도이고 아주 긴 context 가 문장 전체를 실패시키므로). 검색어는 `plainto_tsquery`(모든 어절 AND)로 만들어 연산자 문법 입력이 오류가 되지 않게 한다. 한계: 형태소 분석이 못 쪼개는 신조어 · 오타는 맞지 않는다(의미 검색이 보완).
* **질의 임베딩은 `double precision[]` + `embedding_key`.** `crawl_chunks` 와 같은 방식이다. pgvector 열을 쓰지 않는 이유: 보관 상한이 500건이라 인덱스가 필요 없고, 임베딩 모델을 바꿔도 열 차원이 걸리지 않는다. `embedding_key` 는 모델 이름이다(질의는 바뀌지 않으므로 글 해시가 필요 없다). 검색 때는 `array_length` 가 같은 행만 `::vector` 로 바꿔 pgvector 의 코사인 거리(`<=>`)로 비교하고, 키가 현재 모델과 다른 행은 제외한다.
* **임베딩 시점.** 실행이 시작될 때(insert 직후) 기다리지 않고 계산해 저장하고, 실패해도 실행을 막지 않는다(로그만 남김). 옛 행 백필은 서버 시작 시 백그라운드로 한 번(최근 500건 상한, 16건씩 배치), 그리고 `mode=semantic` 요청이 올 때마다 뒤에서 50건까지(동시에 하나만) 한다. 요청 안에서 기다리며 채우지 않는 이유: 응답 시간이 행 수 · 임베딩 서버 속도에 따라 예측 불가능해진다. 배치가 실패하면 그 백필은 멈춘다(서버가 내려가 있을 때 건건이 실패하지 않으려고). 그 결과 임베딩이 아직 없는 행은 의미 검색에서 빠진다.
* **최소 유사도 `0.8`**(`list/semantic/index.ts` 한 곳). 시드 기본 모델 `embeddinggemma2:mp` 로 잰 값이다: 관련 있는 쌍 0.877 · 0.904 · 0.907, 관련 없는 쌍 0.606 ~ 0.754(이 모델은 무관한 글도 0.6 이상을 준다). 표본이 질의 5개 × 행 2개로 아주 작고 모델이 하나뿐이므로 모델을 바꾸거나 로그가 쌓이면 다시 재야 한다. 결과가 너무 많거나 적으면 이 상수만 고친다.
* **임베딩 서버 실패는 503.** 빈 결과로 돌려주면 「검색됐는데 없다」와 구별되지 않는다. 키워드 검색은 임베딩 서버와 무관하다.

## 확장 방향(미구현)

* **컨테이너 내부 임베딩.** 외부 서버 대신 컨테이너 안에서 임베딩을 돌리려면 Python 프로세스를 하나 더 두어야 하고(이미지 크기와 GPU 접근이 쟁점), 그 서비스가 OpenAI 호환 `/v1/embeddings` 를 내면 AI 서버 설정의 주소만 바꿔 갈아 끼울 수 있다. 서버 코드는 이미 그 계약에만 의존한다.
* **멀티미디어.** LM Studio 류 임베딩 서비스는 텍스트만 지원한다. 이미지 · 음성을 다루려면 위 내부 임베딩 서비스가 멀티모달 모델을 올려야 하고, `ds_*` 와 폴더 조사원도 텍스트 이외 파일을 읽도록 확장해야 한다.

### 코드베이스 토큰화: 밑줄 이름 전체 토큰

snake_case 이름은 조각과 함께 밑줄로 이은 전체(`url_for`)도 색인·질의 토큰으로 남긴다. 조각만 쓰면 질의의 불용어 조각(`for`)이 빠져 정확한 이름 일치가 흔한 조각(`url`) 일치에 묻힌다(Flask `url_for` 질의 실측). 측정: `test/20261115/new-researchers_report.md`.

### 코드 조사원 하나로 여러 프로젝트를 읽는다(`projects`)

* 배경: 호스트 `F:\dev` 아래 프로젝트마다 조사원을 하나씩 만들면 조사원 29개가 되고, 라우터 후보 · 설정 · 관리 화면이 프로젝트 수만큼 늘어난다. 마운트는 처음부터 하나(`DUALCONTEXT_WORKSPACE_DIR` 읽기 전용 바인드)다.
* 결정: `directory` 조사원에 `projects: true` 를 두면 `path` 의 바로 아래 폴더를 프로젝트로 본다(숨김 · `node_modules` · `dist` · `build` 제외). 프로젝트마다 자기 인덱스를 갖는다. 키는 단독 조사원 `path: "workspace/<이름>"` 과 같아 이미 만들어 둔 인덱스를 그대로 쓴다.
* 프로젝트 선택: 한 인덱스에 전체를 넣으면 `maxFiles`(조사원 단위 상한)를 넘으므로 인덱스는 따로 두고 질의 때 고른다. 질의에 프로젝트 이름이 **단어로** 나오면 그 프로젝트만(부분 일치 · 3자 미만 이름은 제외: `p4` 가 `p4studio` 를 끌어오지 않게). 이름이 없으면 이미 인덱스가 있는 프로젝트 전체를 읽는다.
* 한계(검증하지 않은 것): 이름이 없는 질의의 병합 점수는 BM25 가 프로젝트별 인덱스에서 따로 계산돼 엄밀하게 비교되지 않는다. 인덱스가 없는 프로젝트는 뒤에서 하나씩 만들어 질의를 막지 않으므로, 처음 한동안은 이름 없는 질의의 결과가 인덱스가 만들어진 프로젝트로 치우친다. 라우팅 단계에서는 조사원이 하나라, 프로젝트별 설명 · 키워드로 하던 후보 구분은 그 한 조사원의 설명에 프로젝트 이름을 나열해 대신한다.

### 웹 검색어는 질의 원문이 아니라 다시 쓴 문장이다

* 원인(실행 227): 질의 `vibeagent 에서 코딩 에이전트 turn loop 를 분석한 부분` 이 덕덕고에 그대로 나갔고, 웹에 없는 내부 이름 `vibeagent` 가 `vibe` + `agent` 로 풀려 「바이브코딩 강의」 글이 돌아왔다. 질의 원문은 코드 · 자료 조사원용 문장이라 웹 검색어로 맞지 않다. 같은 문자열을 덕덕고에 직접 보내 같은 결과가 나오는 것을 확인했다.
* 결정: 웹 조사원은 채팅 모델에 검색어 한 줄을 만들게 한다(`collect/duckduckgo/rewrite`). 호출 하나가 늘어난다(추론 모델이라 수 초). 실패 · 빈 답이면 원문으로 간다.
* 한계(측정하지 않음): 다시 쓴 검색어가 원문보다 나은 결과를 내는지는 아직 전후 비교로 확인하지 않았다. 웹 프로시저 중복 선택(점수 차 0.03 이내면 2위까지)은 전역 프로시저 라우터 설정이라 이번에 바꾸지 않았다.
