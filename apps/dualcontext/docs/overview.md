# 개요

`dualcontext` 는 「확장된 Dual RAG」를 구현하는 **MCP 서버 + 관리자 사이트** 서비스 모듈이다.
(책의 Dual RAG 구현이 아니라 강사의 확장 해석을 구현한다.)

## MCP 계약

* 도구는 **하나**: `augment_context`. 인자는 질의(`query`)와 선택 `effort`(`light` 기본 · `middle` · `high` · `xhigh`) 뿐이다.
* 응답은 고정 머리(수행 단계 · 충분 여부) + 질의를 증강한 컨텍스트 텍스트다. 답변은 돌려주지 않는다.
* 기본 전송은 stdio. 서비스 자체는 Docker 컨테이너 하나에서 돈다(Node + PostgreSQL/pgvector).

## 내부 동작

1. **조사원 라우팅**(1단계): 질의로 조사원을 상위 N 개 고른다.
2. **수집**: 선택된 조사원이 자기 출처에서 원재료를 모은다(해석하지 않는다).
3. **프로시저 라우팅**(2단계): 조사원마다, 그 조사원에 **연결된** 프로시저 중 상위 M 개를 고른다. 하나도 못 고르면 조사원의 **기본 프로시저**(활성이고 연결된 것)가 대신 붙는다(자료가 없는 조사원은 제외, `internals.md`).
4. **라이터**: (조사원 결과, 프로시저) 쌍 여러 개를 받아 컨텍스트를 만든다. 쌍을 한 번에 받을지(일괄), 쌍마다 따로 호출해 이어 붙일지(쌍별)는 라이터 설정이다. 웹 검색 조사원의 자료는 큐레이션 자료와 섞지 않고 「웹 검색 결과(검증되지 않은 보조 자료)」 섹션으로 뒤에 따로 싣는다(템플릿 · LLM 라이터 공통).

## 용어

| 용어 | 뜻 |
| --- | --- |
| 조사원 | 출처마다 하나. 타입: 덕덕고 웹 검색, pgvector 테이블 벡터 검색, 볼륨 폴더(텍스트 파일), 코드베이스(Git 레포 클론 또는 볼륨 안 코드의 심볼 · 호출 구조 검색). 프로시저를 여러 개 연결한다. |
| 조사원 | 출처마다 하나. 타입: 덕덕고 웹 검색, pgvector 테이블 벡터 검색, 볼륨 폴더(텍스트 파일), 사이트 크롤러(별도 컨테이너에서 렌더링해 청크 임베딩 검색). 프로시저를 여러 개 연결한다. |
| 프로시저 | 사람이 써 둔 분석 절차와 추출할 임팩트 기준. 조사원과 무관하게 독립적으로 존재하고, 연결은 조사원이 지정한다. |
| 라우터 | 질의 분해 방법과, 조사원 · 프로시저를 고르는 라우팅 단계들(키워드 · 임베딩 유사도 · LLM 선택)을 위에서 아래로 쌓은 파이프라인. 저장 전에 「라우팅 미리보기」로 질의 하나의 선택 · 단계별 기록을 본다. 조사원마다 **개별 라우터**를 줄 수 있다(아래). |
| 라이터 | 컨텍스트를 만드는 엔진(기본 조립 · LLM)과 프롬프트, 호출 방식. 활성 라이터 하나를 MCP 가 쓴다. |
| AI 서버 설정 | 임베딩 서버와 LLM 서버 각각의 주소 · 모델 · API 키. |

## 개별 라우터

일부 조사원은 전역 라우터(임베딩 유사도로 후보를 줄 세우는 일괄 판정)로 가리기 어렵다(예: 웹 검색은 「최신 정보가 필요한 질의」라는 성질이 주제 유사도로 드러나지 않는다). 그런 조사원에는 조사원 편집 화면에서 **개별 라우터**를 줄 수 있다.

* 개별 라우터가 있는 조사원은 전역 라우터의 후보 목록(카탈로그, LLM 프롬프트 포함)에서 **빠진다**.
* 질의마다 별개의 프로세스로, 단계(임베딩 · 키워드 · LLM)를 차례로 거쳐 **그 조사원 하나를 쓸지**만 판정한다. 단계를 다 통과해 남으면 포함, 비면 제외한다. 전역 라우터와 같은 단계 종류 · 실패 처리(`onError`)를 쓰고, 하위 질문에는 `parts` 가 켜진 단계만 돈다.
* 포함된 조사원은 전역 선택과 합쳐진 뒤 **같은 경로**(자료 수집 → 프로시저 매칭 → 라이터)로 수렴한다. 프로시저 매칭은 개별 라우터와 무관하게 원래대로다.
* 판정 기록(포함 여부, 단계별 기록)은 라우팅 미리보기와 증강 결과의 `routing.individual` 에 남는다.

## 관리자 사이트

왼쪽 메뉴: 조사원 · 프로시저 · 라우터 · 라이터 · AI 서버 설정 · 시험 실행 · 실행 로그. Claude Code 다크 스킨.
시험 실행은 MCP 도구와 같은 경로를 돌리고, 선택된 쌍과 라우팅 방법(되돌림 포함)을 함께 보여 준다.
시험 실행은 증강한 컨텍스트로 **최종 답변까지** 만들고, 증강 전(질의만) 답변과 증강 후(질의 + 컨텍스트) 답변을 나란히 보여 준다. 최종 답변은 LLM 호출 두 번이라 수 분 걸릴 수 있다.
시험 실행은 성공이든 실패든 로그로 남고, 「실행 로그」에서 **목록**(`#runs`)과 **뷰**(`#runs/<id>`)를 따로 본다.

* 목록: 2줄 항목(1줄 `일시 | 질의` + 작은 상태, 2줄 선택된 조사원들, 둘 다 한 줄 엘립시스)과 페이징(20건). 위쪽에서 조사원 · 프로시저를 여러 개 골라(OR) 거르고, 검색어(키워드 / 의미 임베딩)와는 AND 로 합친다. 필터 · 검색을 바꾸면 1쪽으로 돌아가고, 뷰에서 「목록으로」 돌아와도 필터 · 검색 · 쪽이 유지된다.
* 뷰: 위에 질의 전체, 이 실행의 계획(모드 · 한도), 시각 · 성공 여부 · 소요 시간 한 줄 요약, 삭제 버튼, 실패 사유. 그 아래 왼쪽에 실행 전체를 한 장으로 보는 **그래프**(질의 → 질의 분해 → 분류 그래프 → 답변 → 평가 → 보강 그래프 → … → 최종 답변)가, 오른쪽에 고른 **노드의 상세**(프롬프트 · 라우팅 · 조사원 · 프로시저 · 이전 참고 컨텍스트 · 만들어진 컨텍스트 · 점수와 판정)가 있다. classic 실행도 같은 구조(질의 → 증강 → 답변)다. 진행 중인 실행은 SSE 로 실시간 갱신되며 선택한 노드는 유지된다.

## 사전 정의 조사원

허깅페이스 데이터셋을 `ds_*` 테이블로 적재한 pgvector 조사원 5개(분야 폴더로 21개가 더 있다, `usage.md`)(법률 용어 · 판례·법령 · 의학 문제은행 · 산업 뉴스(합성) · 금융 시황(합성))와 덕덕고 조사원 1개, 이를 위한 프로시저 8개가 처음 한 번 등록된다. 적재는 `seed-data/load-datasets.mjs` 이다(`usage.md`).

## 마땅한 조사원이 없을 때

라우팅이 선택을 하나도 하지 않으면 **컨텍스트를 공급하지 않는다**(MCP 는 빈 결과, 시험 실행은 증강 후 답변을 만들지 않음). 관리자 「라우터」의 최소 유사도로 조절하고, 시험 실행 · 실행 로그에서 후보별 점수를 본다.

## 현재 한계

* 임베딩 · LLM 은 외부 서버에 의존한다. 컨테이너 내부 임베딩(Python)은 아직 없다.
* 폴더 조사원은 텍스트 파일(txt · md · markdown · csv · log)만 읽는다. 멀티미디어는 다루지 못한다.
* 코드베이스 조사원은 정규식 기반 근사 구조 인덱스다(타입 해석 · 파서 없음). 호출 관계는 이름 일치라 같은 이름이 여러 곳에 정의되면 부정확하고, 질의의 영문 식별자 · 단어로만 찾는다(한글만 있는 질의는 결과 없음). 상세는 `internals.md`.
* 덕덕고 조사원은 HTML 결과 페이지를 읽으므로 페이지 구조가 바뀌거나 봇 차단이 오면 실패한다(실패는 컨텍스트의 「찾지 못한 것」에 표시된다).
* 이 확장 정의의 이득은 아직 측정되지 않았다.
